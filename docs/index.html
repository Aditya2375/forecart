How it works

A small deterministic pipeline that is exactly right for a closed catalogue.

01

Re-read everything, every word

The whole request so far is parsed into five catalogue filters: category, colour, size, brand, budget. Nothing is carried over, so nothing goes stale.

02

Last mention wins

"black, no wait, white" and "oh, and in blue" simply change the latest mention of a field. No correction state machine to get wrong.

03

One counted search per change

A lookup runs only when the reading changes and is specific enough to commit on. Repeats are memoised: 1.13 searches per request against 1.53 for the baseline.

04

Commit on a closer, not a guess

Show a product only when it is the unique match of a fully specified reading and the shopper has moved on ("for my brother", "please", "chahiye").

The stress sets come from stress.py, which builds requests from the catalogue with new phrasings, number forms (English and Hindi), synonyms, corrections and late constraints. Running it exposed two latent bugs (an opening "please" counted as a closer, and number words next to "UK" or "waist" read as part of a price); both are fixed and every set now scores zero wrong commits. It is our own generator, so it measures robustness, not the organisers' hidden set. Earliness is modest by design: the agent trades it for zero wrong commits.

Where Rezolve search plugs in

All retrieval goes through one counted call, tools.search.

filters = parse(text_so_far)            # parsing.py
if filters changed and fully specified:  # agent.py
    hits = tools.search(text, filters)   # <- swap this for the semantic-search endpoint
commit only if len(hits) == 1 and a closer was seen

The shipped build runs against the kit's local catalogue search. The wiring point is documented in ARCHITECTURE.md; no Rezolve code is included because no access has been issued yet.
